# ADR-002：碰撞与遮挡一律用解析几何求交，禁止对网格做射线检测

- **状态**：已采纳（Accepted），并已作为性能红线固化
- **日期**：追溯记录（事故驱动决策，事后归档）
- **决策者**：项目作者（事故发生后）
- **影响范围**：`game.js` 的 `raycastObstacles()` / `hasLineOfSight()` / 玩家移动碰撞、`enemy_ai.js` 的 `isEnemyBlocked()` / `findNearestCover()`、`world_props.js` 的 obstacles 登记、`boss_system_v2_extensions.js` 的障碍物遍历

---

## 1. 背景

游戏里的「遮挡」需求有四种完全不同的用法，它们对精度的要求和对调用频率的要求差异极大：

| 需求 | 调用频率 | 精度要求 | 数据量 |
|---|---|---|---|
| **敌人视线**（能不能看见玩家） | 每敌每帧（修复前） | 低（「大部分挡住」就算挡住） | 14–72 个敌人 × 上百掩体 |
| **子弹命中**（打到什么、什么材质、在哪留弹孔） | 每次开枪 + 每颗子弹每帧 | 高（要命中点、法线、surface 类型） | 单次射线 |
| **玩家/AI 移动碰撞**（能不能走过去） | 每个移动者每帧 | 低（不穿墙即可） | 十来个移动者 × 上百障碍 |
| **AI 掩体搜索**（附近有没有躲的地方） | 状态切换时（低频） | 极低（近似位置即可） | 单次遍历 |

修复前的实现统一用了 `THREE.Raycaster.intersectObjects(scene.children, true)`（递归）来处理第 1 类。这是**灾难性的不匹配**：一个需要「低精度、高频率、大批量」的查询，用了「高精度、单次代价高」的实现。

### 1.1 事故：单帧 399 ms，FPS 掉到 3

症状描述（`game.js:4763-4764` 的注释保留了记录）：

> 视线检测：用碰撞体做解析几何求交，避免对建筑窗户等上百个子网格逐三角形射线检测。
> 旧实现每个敌人每帧递归 `intersectObjects`，单帧可达数百毫秒，是低帧率的主因。

可复现的算术：

```
14 个敌人 × 每帧 1 次 intersectObjects
× 场景 ~数万个三角形（3 张地图各 120+ 建筑，每栋有窗户/门/装饰子网格）
× BVH 未加速（r128 的 Raycaster 走线性遍历 + 逐三角形求交）
= 单帧数百毫秒
```

关键点在于**这不是线性变慢，是乘法爆炸**：敌人数量 × 场景三角形数。硬核模式 72 个敌人时，成本是普通模式的 5 倍。

另一个后果是**它无法靠降画质解决**：`PerformanceGuard` 降的是分辨率/阴影/后期，都是 GPU 侧；这个开销在 CPU 侧的逻辑帧里，降画质完全无效。所以表现是「FPS 3 但画面质量没变差」，非常反直觉。

第二次相关事故：**子弹遮挡**如果走网格 raycast，开一枪卡 100–300 ms（同样是逐三角形）。在自动武器上表现为连发时整体幻灯片化。

---

## 2. 决策

**所有「碰撞 / 遮挡 / 命中」查询一律基于 `obstacles` 数组做解析几何求交，禁止对场景网格（`scene` / `mapEnvironmentGroup` / 建筑子网格）做射线检测。唯一的例外是「高频但低频次」的输入路径——即鼠标开火那一刻的一次性 raycast，且必须限定目标集合。**

具体规则：

### 2.1 唯一数据源：`obstacles` 数组

所有可碰撞体必须在建图时登记到全局 `obstacles`（`game.js:1691`），形状为两种之一：

```js
// 轴对齐盒（建筑、集装箱、路障、沙袋、油桶、木箱）
{ mesh, isAABB: true, halfW, halfD, height, climbable?, isWater?, surface? }

// 圆柱（树、灯柱等）
{ mesh, radius, height, surface? }
```

`mesh` 只用来读 `position`（世界坐标）和挂引用，**碰撞计算完全不碰 `mesh.geometry`**。

### 2.2 三种解析求交实现

| 用途 | 实现 | 位置 |
|---|---|---|
| 带法线/命中点的射线（子弹、弹孔） | **slab method**（AABB） / **线段-圆求交**（圆柱），返回 `{distance, point, face.normal, object.userData.surface}` | `raycastObstacles()`，`game.js:4681` |
| 纯遮挡判断（视线，只要布尔） | 只做 **X/Z 双轴 slab**（视线的 y 变化被忽略），跳过 `isWater`，跳过 `height < 1.15` 的低矮掩体 | `hasLineOfSight()`，`game.js:4765` |
| 移动碰撞（只要布尔） | AABB 俯视投影 + 0.6 m 半径膨胀，忽略 `height` | `isEnemyBlocked()`，`enemy_ai.js:550` |

三者的差异是刻意的：

- `raycastObstacles` 需要 **Y 轴 slab**（子弹会打到箱子上沿或从上方掠过）。
- `hasLineOfSight` **不需要 Y 轴**：敌人和玩家都站在地面上，视线是「俯视图上的一条线段」。这省掉 1/3 的计算，且让 `h < 1.15` 的掩体自动不遮挡（低矮箱体不该让敌人「瞎」）。**注意：Y 轴信息的缺失被 `if (h < 1.15) continue` 部分补偿——高掩体（高度 ≥ 1.15 但 < 3）在真实 3D 里可能遮挡不到视线，但这里会判为遮挡。这是刻意的乐观近似（宁可让敌人「看不见」），不是 bug。**
- `isEnemyBlocked` **忽略 height**：AI 移动是 2D 的，它只关心「这片地面能不能站人」。

### 2.3 视线必须节流到 120 ms

`enemy_ai.js:241`：

```js
// 视线 8Hz 足够：缓存结果，避免每帧对全部掩体求交
if (!enemy._losNext || now >= enemy._losNext) {
    enemy._los = hasLineOfSight(enemy, playerGroup.position);
    enemy._losNext = now + 120;   // 毫秒
}
const hasLOS = enemy._los;
```

即使解析求交已经比 raycast 快两个数量级，**仍然要节流**。理由：`obstacles` 在硬核地图上可达 300+ 个元素（120 建筑 + 190 容器 + 道具），72 个敌人 × 每帧 × 300 = 21,600 次 slab 测试/帧，依然是可观的 CPU 开销。120 ms（约 8 Hz）是「玩家侧滑进掩体后敌人反应延迟」的感知阈值——再慢就会觉得敌人「反应迟钝得像傻子」，再快就是浪费。

### 2.4 允许的 raycast 例外

只允许在**低频事件路径**上使用 `THREE.Raycaster`，且必须用预建的两个 raycaster 单例（`playerRaycaster` / `enemyRaycaster`，`far = 250`），不得在循环内 `new Raycaster()`：

- 开火瞬间的敌人命中判定（对 `enemyHitboxes` 而非整个场景）
- 搜索容器时的点击拾取
- `InspectViewer` 里的模型拾取（独立小场景，三角形数极少）

**禁止**：在 `animate()` 的每帧路径上、在 `updateEnemies()` / `updatePlayer()` 内部、在 10 次固定步长循环内，调用 `intersectObject` / `intersectObjects`。

## 3. 后果

### 3.1 正面

- **数量级提升**：视线判断从「单帧数百毫秒」降到「单帧可忽略」。这是本项目最大的一次性能修复，直接决定了游戏能否在核显上跑起来。
- **可预测的成本**：解析求交的复杂度是 `O(obstacles.length)`，与建筑内部有多少窗户、多少装饰子网格**完全无关**。地图美术可以随便加细节而不影响 AI 性能。这是一个非常有价值的解耦：**视觉复杂度与逻辑成本脱钩**。
- **可以精确降级**：需要时可以把 `obstacles` 按玩家距离排序、只检查前 N 个（LOD 化的碰撞），这条路在 raycast 方案下不存在。
- **可测试**：`hasLineOfSight` 的输入是「一个敌人 + 一个点 + 一个 obstacles 数组」，纯函数，可以在无浏览器环境下断言。raycast 版本必须起 WebGL 才能测。
- **`PerformanceGuard` 不需要管它**：CPU 侧的逻辑开销被压到不进入降级决策的层级。

### 3.2 负面

- **`obstacles` 成为全局热点**。它是 L2 的唯一碰撞真值，被 4 个模块以 4 种语义消费（见 `overview.md` §2.2）。任何「新增可碰撞物」都必须登记进去，漏登记 = 新物体「看得穿、走得穿、打不中」。而没有编译期检查会提醒你漏了。
- **`height == null → 3` 的默认值被三处独立实现**。改默认值要同时改 `raycastObstacles`（`game.js:4688`）、`hasLineOfSight`（`game.js:4773`）、以及 `world_props.js` / `createEnvironment` 里的登记处。漏一处就出现「子弹打不中但走不过去」这类不一致。
- **精度上限**：全是 AABB 和圆柱，**没有旋转 OBB**。斜置的掩体只能用外接 AABB 近似，会偏大（玩家会被一个看不见的角挡住）。目前地图数据里建筑都是轴对齐的，所以没暴露问题，但这是一个硬天花板。
- **水面的特殊处理是个特例**：`isWater: true` 的障碍物在 `hasLineOfSight` 里被跳过（视线穿过水面），在 `raycastObstacles` 里 height 默认成 0.05（子弹打在水面）。这种「用布尔标记表达语义分支」的写法会在新增语义（如「玻璃可看穿但不可穿越」）时迅速失控。
- **AI 掩体搜索用了错误的语义**：`findNearestCover()`（`enemy_ai.js:22`）把「障碍物」直接当「掩体」，选了敌人与玩家之间最近的那个。它没考虑掩体高度是否够蹲、没考虑从该位置出来能不能打到玩家。这是一个功能上的偷工，不是性能问题，但和本 ADR 共享 `obstacles` 数据源，改一处会互相影响。

### 3.3 已知残留违规（必须修）

`game.js:3388` 的降级 AI 分支：

```js
if (dist < detectRange && hasLineOfSight(e, playerGroup.position)) { e.state = 'chase'; e.alertTimer = 4; }
```

这段在 `for (let i = enemies.length - 1; i >= 0; i--)` 的循环体内，**每敌每帧调用，无节流**。

当前不会触发，因为 `enemy_ai.js` 正常加载时 `typeof EnemyAI !== 'undefined'` 走的是 `EnemyAI.updateEnemyAI()`。但一旦 `enemy_ai.js` 加载失败（顺序错了、CDN 慢、被 `typeof` 守卫吞掉），`EnemyAI` 变成 `undefined`，就会静默切到这条分支——**那个 399 ms 的 bug 会以「加载失败时的降级路径」的形式复活**，而且无从察觉（因为它是降级路径，看起来「只是流畅度差一点」）。

这是典型的「修复了主路径但留下了地雷」的案例。修法：给降级分支加同样的 120 ms 节流，或干脆删除降级分支（让 `enemy_ai.js` 成为硬依赖）。

## 4. 替代方案

### 方案 A：保留 Raycaster，但加 BVH 加速（`three-mesh-bvh`）（否决）

- **做法**：给 `mapEnvironmentGroup` 建一次 BVH（`three-mesh-bvh` 的 `computeBoundsTree()`），之后 raycast 走 BVH 遍历，复杂度从 `O(三角形)` 降到 `O(log n)`。
- **优点**：保持高精度（真实的窗户缝隙、斜面、楼层高度都能正确处理）。视觉与逻辑完全一致，不会出现「明明有缝但打不过去」。
- **为什么否决**：
  1. `three-mesh-bvh` 是为较新版本 Three.js 写的，r128 兼容性需要验证（**待核实**）。即使能跑，也引入了一个新的 `vendor/` 依赖。
  2. 建 BVH 本身有成本（切图时要重建），而 `rebuildMapEnvironment` 已经在加载路径上是瓶颈之一。
  3. **仍然要节流**：BVH 只是把常数从 1000 降到 20，`O(log n)` 依然是每敌每帧的开销。既然还要节流，解析方案的成本几乎为零，没有理由承担 BVH 的复杂度。
  4. 与 ADR-001 的精神一致：不引入新依赖。
- **保留价值**：如果将来需要「子弹穿过窗户栅栏」这类高精度玩法，这是唯一可行的路径。届时应把用途切分为「视线用解析、命中用 BVH」。

### 方案 B：物理引擎（cannon-es / ammo.js / rapier）（否决）

- **做法**：把 `obstacles` 换成物理世界的静态刚体，用 `world.raycastAny()` 查遮挡。
- **优点**：统一碰撞与物理，可以做物体被炸飞、真实堆叠、布娃娃。
- **为什么否决**：为一次布尔查询引入整个物理引擎（几百 KB + 每帧 `step()`）。当前游戏没有刚体动力学需求——所有物体是静态的，玩家是胶囊做手动移动。引入后每帧固定成本反而更高。
- **备注**：如果未来要做「爆炸把沙袋炸开」这类物理玩法，应重新评估，但即使那时也应该「物理只用于可破坏物，静态建筑仍走解析」。

### 方案 C：网格 + 空间哈希 / 四叉树索引（部分采纳为后续优化）

- **做法**：把 `obstacles` 按地图网格分桶，查询时只检查玩家附近的桶。
- **优点**：把 `O(n)` 降到 `O(k)`，k 是局部障碍物数。对 300+ 障碍物的硬核地图有明显收益。
- **为什么现在不做**：当前 `O(n)` 已经被 120 ms 节流压到可接受。**先测量再优化**——在 `?perfdebug=1` 下如果 `js` 耗时仍在 8 ms 以内，这个优化没有收益。
- **何时该做**：硬核地图敌人数量再翻倍（72 → 150+），或 `obstacles` 因新增道具突破 600 个时。届时应该给 `world_polish.js` 加一个索引构建步骤（它已经在遍历全部静态网格，是天然的接入点）。

### 方案 D：给每个障碍物加「简化的碰撞代理网格」手工维护（否决）

- **优点**：精度介于 AABB 和完整网格之间。
- **为什么否决**：这是「两边都不讨好」的中间态——既没有解析的零成本，也没有网格的精度。而且要求美术/策划同时维护碰撞代理，在单人项目里等于给自己加一道工序。

## 5. 复核触发条件

1. **`obstacles.length` 稳定超过 600** → 评估方案 C（空间索引）。
2. **出现「子弹穿过墙体/被空气挡住」的具体报障** → 说明 AABB 近似不够，评估方案 A 的 BVH，或对特定物体加 OBB 支持。
3. **新增可破坏物/物理互动需求** → 评估方案 B，但限定为「可破坏物专用」，静态建筑不动。
4. **需要「玻璃可看穿但不可穿越」这类新遮挡语义** → 不要加布尔标记，应把 `obstacles` 的元素升级为带 `opacitySemantics` 的策略对象。
5. **`game.js:3388` 的残留违规未修之前** → 任何改动 `updateEnemies` 的 PR 都必须先修它。

---

## 6. 给接手者的一条核心纪律

> **在 `animate()` 的调用栈里出现 `intersectObjects`，就是 bug。**

无论它看起来多方便、精度多好。四种查询（视线/子弹/移动/掩体）全部走 `obstacles` 的解析求交，成本与视觉复杂度脱钩。如果新增的玩法确实需要网格级精度，把它做到事件路径上（点击、开火瞬间），并明确记录为什么它是例外。
