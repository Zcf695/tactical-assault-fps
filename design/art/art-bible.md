## 一、视觉身份

### 一句话

> **被 30° 晨光斜切过的工业现场——冷调暗部、暖调高光、每个表面都粗糙到能看清骨料。**

### 三个关键词

| 关键词 | 含义 | 落地手段（对应代码） |
|---|---|---|
| **低角度强对比** | 单一方向光 + 极弱环境光，阴影是构图的一部分，不是被消灭的瑕疵 | 太阳仰角 29.9°，受光/背光理论比 ≈ 5.5 : 1（见 §4） |
| **骨料质感** | 没有"光滑表面"。混凝土有麻点、沥青有骨料、金属有锈斑、沙袋有编织 | 12 套程序化 roughness/normal，roughness 区间 0.86–0.97，`pbr_textures.js` |
| **克制再现** | 血液低饱和、火光短促、没有霓虹没有卡通描边，表现强度服从可读性 | 血雾 `0x8a2a26` 且仅 8 颗粒；枪口火焰 **55 ms**（`weapon_fx.js:233`） |

### 反目标（明确不做）

- 不做"卡通渲染 + 描边"（与 GLB 写实系敌人、PBR 地面冲突）
- 不做"高饱和战术滤镜"（会盖掉 ACES 分离色调建立的冷暖分层）
- 不做"赛博霓虹"（`--accent: #ff9800` 是唯一强调色，全局只有一个强调色）

## 二、风格定位

### 2.1 写实度刻度

| 刻度 | 0–2 | 3–4 | **5–7（本项目）** | 8–9 | 10 |
|---|---|---|---|---|---|
| 描述 | 抽象几何 | 低多边形扁平 | **可信的工业写实** | 照片级材质 | 影视实拍 |
| 几何 | 纯色块 | 少面数 + 硬边 | 中低面数 + 立面细节 + 程序化噪声法线 | 高模 | 扫描 |
| 材质 | 纯 Lambert | 纯色 Standard | **程序化 PBR（256²，4 通道）** | 4K 扫描贴图 | 位移 |
| 光照 | 无方向 | 单灯 | **方向光 + 半球 + 反弹补光 + PMREM IBL** | 实时 GI | 光追 |

**定位：6.5 / 10。** 判据三条：

1. 玩家在 3 m 内看得清地面骨料与墙面麻点，但看不清法线贴图的像素格（256² / 5.5 m tile ≈ 2.2 cm 一个纹素，正好是"看清质感、看不清像素"的甜点）。
2. 建筑是 BoxGeometry 拼装，靠**立面分层**（腰线 / 窗框 / 窗台 / 雨棚 / 女儿墙）建立可信度，而不是靠高模。
3. 敌人是外部 GLB（`models/Soldier.glb` 2.1 MB、`Xbot.glb` 2.9 MB、`RobotExpressive.glb` 464 KB），几何精度**高于**场景，属于"人物比环境更精细"的正常取舍。

### 2.2 为什么选程序化，而不是贴图包

| 理由 | 依据 |
|---|---|
| **零依赖、离线可跑** | 双击 `index.html` 即可运行是核心卖点（`README.md` Quick Start）。外部贴图包在 `file://` 协议下会被 CORS 拦死 |
| **可无缝平铺由算法保证，不靠人工修边** | `hash2()` 在整数格点上取模（`pbr_textures.js:35-51`），`(x+period)` 与 `x` 同值 → 数学上必然无缝 |
| **一张贴图全局共享，无显存爆炸** | `get()` 缓存 + `applyToMesh()` 只缩放 UV 不改贴图（`pbr_textures.js:492-503, 520-560`）→ 12 套贴图服务上百个网格 |
| **参数即风格** | 想调"更脏"只改 `albedo()` 里的 `stain` 系数；换成贴图包就得回 Photoshop |
| **可确定性复现** | 固定 seed → 每次生图完全一致，便于回归对比 |

**代价（必须承认）**：无 detail map / 无 AO map / 无 curvature map；近看 30 cm 内会露馅。因此本项目的"近景"只到 3 m，第一人称武器与检视模型走另一条线（`item_models.js` 的 `M.*` 材质，见 §5.4）。

### 2.3 与低多边形 / 卡通敌人模型如何共存

**现状（关键冲突，需拍板）**

`game.js:3283` 按等级分配模型：`elv>=3 → RobotExpressive`、`elv===2 → Xbot`、`elv===1 → Soldier`。

- `Soldier` / `Xbot`：偏写实比例的示例模型，与场景尚可共存。
- **`RobotExpressive`：明确卡通风格（大圆头、白身橙饰）**，与"程序化写实"定位直接冲突，且它恰好是**最高等级敌人**——玩家最需要紧张感的对象，长得最像玩具。

**三条桥接规则（无论最终选哪个方案都必须遵守）**

| 规则 | 做法 | 原因 |
|---|---|---|
| **R1 比例锚定** | 敌人模型统一 `scale 0.9`（`game.js:1780`），身高对齐 **1.75 m**（`headMarker.position.y`，`game.js:3291`） | 玩家对"人有多高"极其敏感；比例错 = 廉价感第一来源 |
| **R2 材质降噪** | 敌人贴图若为纯色/无 PBR，在遍历时给所有 MeshStandardMaterial 设 `roughness = max(0.6, 原值)`、`metalness = min(0.4, 原值)` | 场景高粗糙、敌人高光滑是最大的"贴纸感"来源 |
| **R3 光照同源** | 敌人**不得**自带灯光或 emissive 常亮；受同一盏 `sun`（`0xffe2b8`）照明，阴影由 `castShadow` 统一开启 | 一旦敌人自带光，就会从场景里"浮"出来 |

**三个可选方案（需用户拍板，见 §9 末尾"待决策"）**

- **A（最低成本）**：`RobotExpressive` 只保留给"机械 Boss"，等级 3 的人类敌人改用 `Xbot`。承认机械单位可以卡通，人类不行。
- **B（推荐）**：全部敌人统一为 `Soldier`，用材质重染（`0x3a4030` 军绿 + `0x2a2a2a` 装具）+ 肩章色区分等级。牺牲辨识度换统一度。
- **C（最高成本）**：用 `item_models.js` 同样的"几何体拼装"思路做程序化士兵，彻底消除外部资源。

## 四、光照与天气

### 4.1 光照基线（【现状】`render_pipeline.js:322-367`）

| 光源 | 颜色 | 强度 | 参数 |
|---|---|---|---|
| 太阳 `_sun`（DirectionalLight） | `0xffe2b8` | **1.35** | 投影开启（`shadowQuality !== 'off'`） |
| 反弹补光 `_bounce`（DirectionalLight，`castShadow=false`） | `0x9fbfd6` | **0.42** | 位于 `-sunDir × 70`，`y = 32`，只提亮阴影不产生二次投影 |
| 半球光 `_hemi` | 天空 `fog.lerp(0xbcd8ee,0.45)` / 地面 `groundColor×0.7` | **0.22** | 避免阴影死黑 |
| 环境光 `_ambient` | `0x6c8ba5` | **0.06** | 仅用于补最暗处的色相 |

> ⚠️ **`game.js:1960-1971` 存在另一套"旧光照"**：`AmbientLight(0x8899aa, 0.5)` + `DirectionalLight(0xffeedd, 0.7)` + `HemisphereLight(0x8899cc, 0x443322, 0.3)`。若 `RenderPipeline.init()` 失败（WebGL 后期库缺失、异常回退），画面会停留在**旧光照**：环境光 0.5 是正常值的 **8.3 倍**，画面会整体发灰、阴影全无。这是本次审计发现的最危险的美术事故点，见 §9-A。

### 4.2 太阳几何

| 项 | 值 | 出处 |
|---|---|---|
| 方向向量 | `(0.54, 0.50, -0.68)`（已 normalize） | `render_pipeline.js:63` |
| 仰角 | **29.9°**（`atan(0.50 / √(0.54²+0.68²))`） | 由上式算出 |
| 方位 | 从 `-Z` 偏向 `+X`（约东南偏东），即**出生点左后方** | 注释 `:62` |
| 光源距离 | 95 m（跟随玩家水平位置） | `:376-380` |
| 重算阈值 | 玩家每移动 **2.5 m** 才重算一次 | `:373` |
| 投影长度 | **≈ 1.73 × 物体高度**（`1/tan30°`）。6 m 围墙投影 10.4 m，14 m 哨塔投影 24.2 m | 由仰角算出 |

**为什么是 30°**：低于 20° 时阴影过长，会在地面上互相吞没，搜打撤的"藏跑线"读不出来；高于 45° 则立面受光均匀、缺少体积。30° 让**立面有明暗分层、地面有清晰长影**。

### 4.3 阴影策略（【现状】`:330-350`）

| 项 | 值 |
|---|---|
| 阴影相机范围 | `ext = 68` → 覆盖玩家周围 **136 × 136 m** |
| 近/远平面 | `near 1` / `far 220` |
| 贴图尺寸 | `low 1024` / `medium 1536` / `high 2048` |
| 类型 | `low: BasicShadowMap` / `medium: PCFShadowMap` / `high: PCFSoftShadowMap` |
| 偏移 | `bias -0.0007`，`normalBias 0.04` |
| 接地阴影（额外一层） | `WorldPolish`：径向渐变贴片，中心 alpha **0.55**，合并为 1 个 InstancedMesh（1 draw call） |

> **注意双阴影叠加**：`WorldPolish` 的接地阴影中心 0.55 是"假 AO"，与真实投射阴影叠加时，物体根部会明显过黑。§5 给出整改判据。

### 4.5 可执行光照规则

### 4.6 低配降级的美术底线（对 `performance_guard.js` 的要求）

**现状（不可接受）** `performance_guard.js:87-88`，level ≥ 3 时：

```js
if (m.normalMap) { m.normalMap = null; dirty = true; }
if (m.envMapIntensity > 0.1) { m.envMapIntensity = 0.1; dirty = true; }
```

**四条反对理由**

0. **已实测（质量侧 SMK-14，干净页面 level 0 → 3）**：一次降级被置空 `normalMap` 的材质 **424 个**；shader program **20 → 39（+95%）**；`material.map` 被置空 **0 个**。第 2 条与第 3 条由实测坐实，非推测。
1. **几乎不省性能。** `normalMap` 是 1 次纹理采样。实测瓶颈是 draw call（1050）与填充率，不是纹理带宽——砍它对批次毫无帮助。
2. **反而制造卡顿。** `normalMap = null` + `needsUpdate` 触发**每个材质的 shader 重编译**，而且发生在机器已经掉帧的时刻，是最糟的时机。
3. **抹掉的是美术定位本身。** 三关键词之二的「骨料质感」100% 来自 normalMap；12 套材质的 albedo 都只是低对比噪声。同时 `applyToMesh` 把 `roughness/metalness` 固定设 1.0 作为贴图乘子 → 表面会退化成**均匀全哑光**，连高光形状都丢失，等于把 PBR 降级成"印了花纹的墙纸"。
4. **`envMapIntensity → 0.1` 在 lowMode 下是空操作。** level 3 会走 `setLowMode(true)` → `scene.environment = null`，此时该值不参与计算；只在"关后期但未进 lowMode"的中间态误伤金属/水/玻璃。

**美术侧底线（替代方案）**

| 项 | 规定 |
|---|---|
| `material.map`（albedo） | **永不置 null** |
| `material.normalMap` | **永不置 null**；降级只改 `normalScale × 0.5`（改 uniform，**不触发重编译**） |
| `roughnessMap` | 保留（它决定"哪里湿哪里干"，是 PBR 的另一半） |
| `envMapIntensity` | 仅当 `scene.environment !== null` 时才压，**下限 0.12**（地面 0.18 → 0.12，-33%，肉眼几乎无差） |
| 真正的性能杠杆 | 分辨率（已有 0.65/0.55）、关阴影（已有）、**合批**（§6.4） |

**验收项（已提给质量侧写入 smoke-cases）**

- [ ] level 3 与 level 0 截图对比，2 m 处墙面/地面仍能看出法线凹凸（人工目检 + 存档，不做像素 diff）
- [ ] level 3 降级**不得**使 `renderer.info.programs` 增加（防重编译）
- [ ] level 3 降级**不得**使 draw call 增加
- [ ] 任何降级动作都不允许把 `material.map` 设为 null

### 5.1.1 纹素密度规范（唯一可量化的材质验收阈值）

**不要用"UV 跨度"做验收。** UV 跨度 = `mapSize / tile`，换个几何体或地图尺寸就失效，且极易被源码里的字面默认值误导（`CONFIG.mapSize` 字面是 110，运行时被 `MAP_DATA.mapSize` 覆盖成 300，见 `game.js:18` vs `game.js:1067`）。

**用纹素密度（cm/texel）**——它同时能抓"太细"（摩尔纹、远景噪点）和"太粗"（发糊、没有质感）：

```
cm/texel = tile(m) / 贴图边长(px) × 100
达标区间：1.0 – 1.3
```

| 材质 | 用途 | 分辨率 | tile | cm/texel | 判定 |
|---|---|---|---|---|---|
| `grass` | 地面（三图共用） | 512² | 5.5 | **1.07** | ✓ |
| `asphalt` | 路面 | 256² | 3.2 | **1.25** | ✓ |
| `gravel` | 岸边 | 256² | 3.2 | 1.25 | ✓ |
| `concrete` | 边界围墙 | 256² | 3.0 | 1.17 | ✓ |
| **`concrete`** | **建筑立面** | 256² | **4.0** | **1.56** | 🔴 全场最粗，发糊 |
| `roof` | 屋顶 | 256² | 2.5 | 0.98 | 🟠 略细 |
| `corrugated` | 集装箱 | 256² | 2.4 | 0.94 | 🟠 略细 |
| `concreteDark` | 掩体 | 256² | 2.2 | **0.86** | 🟠 全场最细，易摩尔纹 |

**两条验收断言**

1. 所有表面的 `cm/texel ∈ [1.0, 1.3]`。
2. 任意两表面 `cm/texel` 比值 ≤ **1.5**（现最大 1.56/0.86 = **1.81**，超标）。

**【建议】唯一要改的一处（建筑立面）**：`tile 4.0 → 3.2`（1.56 → 1.25，与路面/岸边对齐）。副产品是混凝土分缝从 2.0 m 面板变 1.6 m，更接近真实模板尺寸，立面更"硬"。改前须先出近景对比图。

**⚠️ 地面 tile 必须按贴图边长推导，不能写死 5.5。**
`graphics_enhancement.js:710` 对所有地面种类都传 `tile: 5.5`。这个值是按 `grass`（**512²**）调的 → 1.07 cm/texel ✓。但表 A 把军事/港口换成 `gravel` / `asphalt`（都是 **256²**）后，同一个 5.5 就变成 **2.15 cm/texel**，粗了整整一倍，实测截图里砾石颗粒呈 20–30 cm 的糊块。

```js
// 正确写法：tile 随贴图边长走，保证三种地表纹素密度一致
const _res = PBRTextures.get(groundKind).size;      // grass 512 / 其余 256
const _groundTile = 2.75 * (_res / 256);            // 512→5.5 ✓  256→2.75 ✓
```
校验：`300 / 5.5 = 54.545`（grass）、`300 / 2.75 = 109.09`（gravel/asphalt），两者 cm/texel 均为 **1.07**，比值 1.00 ≤ 1.5 ✓。

### 5.1.2 地面 UV 跨度的正确预期值（避免误判为缺陷）

| 量 | 计算 | 值 |
|---|---|---|
| 运行时 `CONFIG.mapSize` | `MAP_DATA.mapSize`（三图均 300） | **300** |
| 地面 `PlaneGeometry` 边长 | `CONFIG.mapSize` | 300 m |
| `scaleUVs` 缩放系数 | `w / tileU = 300 / 5.5` | **54.545** ← 即设计值 |
| 等效平铺尺寸 | `300 / 54.545` | **5.5 m** |

### 5.2 🔴 最该优先统一的材质规范：**植被**

| 问题 | 证据 |
|---|---|
| `map.trees` 生成的树**完全没有 PBR**，只有纯色 + `roughness` | `game.js:2115-2127`：树干 `0x4a3020` r0.9、树冠 `0x2a5a2a` r0.85，无 normalMap |

### 6.4 🔴 合批率的结构性瓶颈（两个，按影响排序）

#### 瓶颈 ①：搜索容器完全在合批范围之外 —— 占 draw call 的 ~1000

实测 draw call **1050–1103**（headless SwiftShader，军事禁区，兜底画质）。三角面仅 370k、JS 帧耗时 3.9 ms → **瓶颈在绘制批次，不在多边形**。

根因不是建筑，也不是装饰，是**玩法用的搜索容器**：

```js
// game.js:5028  createContainer() 末尾
grp.position.set(x, 0, z); scene.add(grp);      // ← 直接挂 scene

// game.js:2008  合批只遍历地图组
WorldPolish.batchStatic(mapEnvironmentGroup);   // ← 容器永远进不去
```

单个容器 4–7 个 Mesh（长箱 6 / 医疗箱 4 / 设备箱 6 / 保险箱 4），**每个部件都 `new MeshStandardMaterial`**（`game.js:4946` 起）。军事禁区 `containerCount.normal = 200`：

> **200 × 5.5 ≈ 1100 draw call。** 与实测 1050–1103 吻合。也就是说，**约 1000 个 draw call 来自玩法对象，不是美术资产**——减面数、减装饰都是错方向。

| 优先级 | 动作 | 预期 | 风险 |
|---|---|---|---|
| ① | 容器纳入合批（`batchStatic` 二次传参，或 `createContainer` 末尾挂入可合批组）。原网格隐藏后仍可供 Raycast 命中——`world_polish.js:210-214` 已确认此前提 | 1050 → **250–350** | 低；须保留 `containers[].mesh` 引用 |
| ② | 若①因"搜索后需改外观"受阻：按 `type × 材质` 用 `InstancedMesh`，压到 7 型 × 6 件 ≈ **40 dc**，已搜索态用 `instanceColor` 置灰 | 1050 → **约 200** | 中；Raycast 需取 `instanceId` 映射回容器索引 |

#### 瓶颈 ②：建筑墙身每栋一个材质，永不合并

`world_polish.js:114-130` 的 `_materialKey()` 把 `color.getHexString()` 纳入签名。而 `game.js:2215` **在建筑循环内 `new` 一个新材质**，颜色是 `b.color.lerp(...)` 的浮点结果 → **每栋建筑颜色都不同 → 每栋建筑的墙身只能单独一次 draw call**。

> 后果：合批后 draw call 下限 ≈ 建筑数（145 / 113 / 113） + 其余合并组。对"中"档 400 的预算尚可接受，**但一旦加一档画质或加装饰立刻爆表**。

**整改建议（低成本高收益）**：把每张地图的建筑色**量化到 8 色 palette**，`wallMat` 全局缓存复用。

```js
// 建议实现（示意，需 程基岩 落地）
const _wallPalette = new Map();
function getWallMat(hex) {
  const key = (hex >> 4) << 4;              // 丢弃最低 4 bit，256 色 → 16 色
  if (!_wallPalette.has(key)) {
    _wallPalette.set(key, new THREE.MeshStandardMaterial({
      color: key, roughness: 0.78, metalness: 0.0,
    }));
  }
  return _wallPalette.get(key);
}
```

效果：墙身材质从 145 个降到 ≤ 16 个 → 墙身 draw call **-130**。同时解决 §3.4 的配色收敛问题（palette 可按图手工指定）。

**三条合计预期：1050 → 150–200 dc**，进入"中"档 400 预算区间。

## 八、VFX 语言

### 8.1 通用原则

1. **短、亮、快收。** 火光是"事件"不是"效果"，超过 100 ms 就会变成装饰。
2. **亮度服从对比。** 任何加色混合的 VFX，其峰值亮度上限由 Bloom 阈值 `0.86` 反推——低于 0.86 的东西不会发光，会脏。
3. **对象池，运行期零分配。**（`weapon_fx.js` 已完全遵守，见文件头注释）
4. **低配降级只砍数量，不砍时长。**（`weapon_fx.js:240, 350` — `_low` 时跳过硝烟/火花/抛壳，但枪口火焰保留）

## 附录 B：需要用户拍板的美术方向

1. **敌人模型方案 A / B / C**（§2.3）。当前 `RobotExpressive`（卡通机器人）是最高等级敌人，与"程序化写实"直接冲突。
2. **地图差异强度**。修订配色表（§3.6）会把三张地图从"几乎一样"拉到"一眼可辨"。是走"强差异"（大气/地表/屋顶全不同）还是"弱差异"（仅大气不同、地表统一）？影响玩家地图记忆与美术工作量。
3. **`groundSurface` 是否按图区分**。军事 → `gravel`、密林 → `grass`、港口 → `asphalt` 是最省事的差异化手段（改 1 行配置/图），但会改变三张图的"脚感"与载具/跑动反馈预期，需与玩法侧对齐。
