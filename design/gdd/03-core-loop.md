## 1. 三段循环总览

```
┌─────────────┐      ┌──────────────────────┐      ┌─────────────┐
│  准备阶段    │ ───→ │     行动阶段          │ ───→ │  结算阶段    │
│  （大厅）    │      │  （局内 1200/900s）   │      │             │
└─────────────┘      └──────────────────────┘      └─────────────┘
       ↑                       │                          │
       └───────────────────────┴──────────────────────────┘
                        成长回流（资金/装备/XP/技能点）
```

| 阶段 | 时长 | 玩家在做的事 | 心理目标 |
|------|------|-------------|----------|
| 准备 | 30s–3min（自由，不强制） | 配装、买弹药、看任务、点技能、选图选难度 | 规划风险 |
| 行动 | **1200s（常规）/ 900s（高危）** | 搜刮、战斗、向撤离点移动 | 累积与焦虑 |
| 结算 | 5–15s（结算界面） | 看带出价值、XP、任务进度 | 释放与归属 |

> **⚠️ 首要偏差**：README:34 与规划文档 `游戏机制与内容丰富计划.md:29` 描述的「15 分钟 / 10 分钟」与「15–25 分钟」均与代码不符。**代码实际是 20 分钟 / 15 分钟**，因为 `loadMapData()`（`game.js:1068`）用地图数据覆盖了 `CONFIG.gameTime`：

| 参数 | `CONFIG` 声明 | 地图实际 | 生效值 |
|------|--------------|----------|--------|
| `gameTime.normal` | 900s | 1200s | **1200s** |
| `gameTime.hard` | 600s | 900s | **900s** |

## 2. 准备阶段（大厅）

### 2.1 玩家可做的决定

| 决定 | 选项 | 影响 | 出处 |
|------|------|------|------|
| 选图 | 军事禁区 / 密林前哨 / 工业港 | 容器数量 170 / 86 / 78；建筑密度不同 | `map/*.js` |
| 选难度 | 常规 / 高危 | 敌人 14→24，敌人属性 ×1.4~1.5，容器 +26/26/20，**入场费 ₵200,000** | `game.js:21-22`、`3304-3311`、`4838`、`9893` |
| 配装 | 主武器×2 + 副武器 + 匕首固定 + 甲 + 盔 + 胸挂 + 背包 | 决定死亡损失的上限 | `game.js:1638-1647` |
| 带药 | 口袋 5 格 + 胸挂（实际无效，见 02-systems-index D-13） | 决定续航 | `game.js:1651` |
| 点技能 | 3 树共 18 个技能点 | 全局增益 | `game.js:4433-4473` |
| 存配装 | 可存多套 loadout | 复用 | `game.js:8176-8430` |

### 2.2 准备阶段的问题

- 🟡 **入场费 ₵200,000 在经济上是零门槛**。按 §5 的实测，一次短途（10 箱）撤离期望带出 ₵1.9M–₵6.6M。入场费仅是单局收益的 3%–10%，不构成风险决策，只是一个形式上的「惩罚」。
- 🟡 **无「本局预期损失」提示**。玩家配装时看不到「你这一身值多少 ₵」的总价，无法做风险量化。支柱一（风险可计算）在准备阶段失守。
- 🟡 **初始资金 ₵1,000,000**（`game.js:1572`）加上默认仓库（手枪 + 绷带×2 + 止痛药，`game.js:1567-1570`），第 1 局就能配出完整装备。**没有「穷」的阶段**。

## 3. 行动阶段（局内节奏）

### 3.1 时间轴（常规模式，军事禁区）

```
0s        开局：出生点 (0,-135)，距「南撤离点」仅 10m
          ├─ 默认手持匕首（S.currentWeapon=3），需切枪
          ├─ 14 个 AI 随机散布，距玩家 ≥22m
          └─ 8 个撤离点，约 4.8 个初始开启（60%概率）

60–120s   首次空投（airdropTimer = 60 + rand×60）
          └─ 空投可搜索，是中期第一个确定性收益点

持续      搜刮：单箱平均 5.52s（含逐件揭示）
          战斗：遭遇即交火，AI 在 28m 内发现玩家（高危 35m）
          撤离点状态每 40–210s 翻转一次，有全局文字提示

1200s     倒计时归零 → endGame(false) → 判「阵亡」
          ⚠️ 超时与死亡走同一分支，损失规则完全相同
```

### 3.2 节奏曲线设计意图 vs 实际

| 时间段 | 设计意图 | 代码实际 | 判定 |
|--------|----------|----------|------|
| 0–60s | 建立方向感，走向第一个热点 | **可原地按 F 撤离**（见 §3.3） | 🔴 张力归零 |
| 60–300s | 第一波收获，首次危险遭遇 | 空投出现；14 个 AI 中期望约 0.8 个在 100m 内 | 🟡 遭遇稀疏 |
| 300–900s | 深入中心区，贪婪峰值 | 与边缘区无机制差异，仅容器价值略高 | 🟡 无「深处」概念 |
| 900–1200s | 撤离压力，最后的冒险 | 时间仍充裕（清空全图仅需 799s 纯搜刮） | 🔴 压力不存在 |

### 3.3 🔴 关键缺陷：出生点即撤离点

三张地图的 `playerSpawn` 与某个 `extracts` 坐标**几乎重合**：

| 地图 | 出生点 | 最近的撤离点 | 直线距离 | 步行耗时（8 m/s） |
|------|--------|-------------|----------|------------------|
| 军事禁区 | (0, −135) | 南撤离点 (0, −145) | **10 m** | 1.3s |
| 密林前哨 | (0, −130) | 南撤离点 (0, −135) | **5 m** | 0.6s |
| 工业港 | (0, −130) | 南撤离点 (0, −135) | **5 m** | 0.6s |

出处：`map/military_base.js:303,549`、`map/forest_outpost.js:379`、`map/industrial_port.js:353`。

**后果**：
1. 玩家开局 0.6 秒就能站进撤离圈，8 秒后「撤离成功」。整局零风险。
2. 搜打撤品类的核心张力——**「我带着身家，必须穿过危险区回家」**——在本作中不存在。玩家可以在拿到东西后**任何时候**从最近的边缘撤离点离开，而最近的边缘撤离点在出生点。
3. 8 个撤离点全部位于地图边缘（坐标绝对值 125–145，地图半边 150）。**没有任何一个撤离点位于中心区或需要穿越中心区才能到达。**

|--------|------|----------|------|

| 地下通道撤离 | (−135, −135) | 135 m | 描述需紫色钥匙卡（未校验） |
| 村庄小路撤离 | (135, −125) | 135 m | 描述「随机开启」 |
| 东撤离点 | (145, 0) | 198 m | |
| 西撤离点 | (−145, 0) | 198 m | |
| 港口海路撤离 | (135, 75) | 250 m | 描述需船只（未校验） |
| 北撤离点 | (0, 145) | 280 m | 最远 |

> **修复建议（需主理人裁定）**：至少一选其一
> - (a) 出生点内移（如 z = −60），使最近撤离点 ≥70m；
> - (b) 撤离点全部外移到地图边界外（|x| 或 |z| = 165+），且必须穿越至少 1 个建筑群；
> - (c) 引入「撤离需先激活」机制（如携带特定物品或触碰两个塔台）。
> 当前状态直接违背支柱一。

### 3.4 时间预算分析（关键洞察）

**开箱耗时（按代码逻辑精确复算）**：

> **⚠️ 前提更正**：`CONTAINER_TYPES[*].searchTime`（0.8–3.0s）是**死字段**。它唯一被读取的位置是 `startSearchAnimation()`（`game.js:5201`），而该函数**在全代码库中从未被调用**——`interact()` 直接走 `openSearch()`（`game.js:5282`）。因此右侧那个「搜刮进度条」(`#searchProgressOverlay`) 从不显示，开箱耗时**只等于逐件揭示的时长之和**。

| 容器 | 声明的 `searchTime`（未生效） | 期望件数 | 单件平均揭示 | **实际单箱耗时** |
|------|------------------------------|----------|-------------|-----------------|
| medBox | 1.2s | 3.5 | 0.55s | **1.91s** |
| supplyBox | 1.0s | 3.0 | 0.70s | **2.10s** |
| ammoBox | 0.8s | 4.5 | 0.50s | **2.25s** |
| equipBox | 1.5s | 3.0 | 1.02s | **3.06s** |
| weaponBox | 1.5s | 3.0 | 1.03s | **3.10s** |
| safe | 2.5s | 2.0 | **3.65s** | **7.31s** |
| premiumBox | 3.0s | 2.0 | **3.72s** | **7.45s** |
| **7 类平均** | — | — | — | **3.88s** |

**结论**：

| 指标 | 数值 |
|------|------|
| 军事禁区容器总数 | 170 |
| 全图清空纯搜刮耗时 | **559s = 9.3 分钟** |
| 局时长 | 1200s = 20 分钟 |
| 搜刮占用比例 | **47%** |
| 剩余移动/战斗预算 | 641s，按有效移速 ≈10 m/s 可移动 **6,410 m**（绕图 21 圈） |
| 1200s 内理论可开箱数（不计移动） | **309 个 > 全图 170 个（1.8 倍）** |

> **结论：时间限制不是限制，缩水比预想更严重。** 一个玩家在一局内可以清空整张地图的所有容器，只花掉 47% 的时间。规划文档设想的「撤离倒计时制造压力」（`游戏机制与内容丰富计划.md:29`）**在数值上完全不成立**。
>
> 真正限制玩家的是**负重（70kg）与背包格数**——这才是本作事实上的「撤离压力」。设计语汇应从「时间压力」改写为「容量压力」。
>
> **附带发现**：`searchTime` 死字段意味着原本设计的「搜刮有前摇、前摇中被打断」的机制**整个不存在**。开箱瞬间即进入揭示，玩家没有任何「正在翻箱子不能动」的脆弱窗口——只有揭示期间不能开枪（`game.js:2795`）。这削弱了支柱二的紧张感。

| 指标 | 常规 | 高危 |
|------|------|------|
| 实际生成上限（`createEnemy` 硬卡） | **14** | **24** |
| 地图面积（300×300） | 90,000 m² | 90,000 m² |
| **单敌覆盖面积** | **6,429 m²** | 3,750 m² |
| 等效间距（正方网格） | **80 m** | 61 m |
| 地图声明 `enemyCount` | 50 | 75 |

## 4. 结算阶段

### 4.1 成功撤离

| 项 | 规则 | 出处 |
|----|------|------|
| 资金 | `P.money += S.lootValue` | `game.js:10026` |
| 装备返还 | 武器/甲/盔/胸挂/背包 → 仓库，仓库满则进邮箱 | `game.js:10037-10038` |
| 背包物品 | 全部 → 仓库/邮箱 | `game.js:10039` |
| 安全箱物品 | 全部 → 仓库/邮箱 | `game.js:10040` |
| 钥匙链 | 保留 | `game.js:10042-10043` |
| XP | `50 + floor(lootValue × 0.1)` | `game.js:10031` |
| 任务 | `extract_success +1`、`earn_money +lootValue`、价值≥10万则 `extract_value +1` | `game.js:10027-10029` |
| 成就 | `extracts +1`、`extract_value +lootValue` | `game.js:10034-10035` |

### 4.2 阵亡 / 超时

| 项 | 规则 | 出处 |
|----|------|------|
| 资金 | **不扣** | `game.js:10051-10065`（无扣款语句） |
| 安全箱 | **保留**，物品进仓库/邮箱 | `game.js:10054` |
| 钥匙链 | **保留** | `game.js:10056-10057` |
| 背包 / 装备 / 武器 / 口袋 | **全部清空** | `game.js:10060-10064` |
| XP | **0**（不调用 `gainXP`） | 同上 |
| 任务/成就 | 仅 `survive_time` 被调用，但因 `S.phase='gameover'` 被拦截（D-15） | `game.js:10017` |

### 4.3 结算阶段的问题

- 🔴 **超时 = 阵亡，损失规则完全相同**。玩家在撤离点外被时间杀，和被打死，拿到的惩罚一样。这抹掉了「差一点就撤出去」的遗憾美学——本来应该是「你丢下了背包但保住了命」的中间态。
- 🔴 **结算界面不显示「你丢了什么」**。`renderResultLoot`（`game.js:10076-10090`）只显示成功带出的物品。阵亡时这一栏是空的，玩家看不到自己损失了价值多少的东西。**这是搜打撤最重要的情绪反馈缺失。**
- 🟡 阵亡不给 XP。理论上搜索容器已给了 XP（每个 +5，`game.js:5223`），但撤离奖励 0，导致「送死流」和「成功流」的 XP 差距没有体现。

### 5.2 🔴 掉落池价值分布（严重失衡）

| 价值区间 | 池中物品数 | 占比 |
|----------|-----------|------|
| 0 – 10,000 | 30 | 9.1% |
| 10,000 – 50,000 | 32 | 9.7% |

| 200,000 – 500,000 | 69 | **20.8%** |
| 500,000 – 1,000,000 | 55 | **16.6%** |

**全池价值分位**：p10 = ₵10,000 · p50 = ₵550,000 · p90 = ₵3,200,000 · max = ₵15,465,000

**根因**（`game.js:613-614`）：
```js
CONTAINER_TYPES.safe.items = CONTAINER_TYPES.safe.items.concat(_rcIds);      // 93 件红藏品
CONTAINER_TYPES.premiumBox.items = CONTAINER_TYPES.premiumBox.items.concat(_rcIds);
```

| 指标 | 数值 |
|------|------|
| `safe` 池大小 | 121 项，其中 **93 项是红藏品（ultimate）** |
| 单件是红藏品的概率 | **76.9%** |
| 开一箱（期望 2 件）至少含 1 件红藏品的概率 | **94.6%** |
| `premiumBox` 单件是红藏品概率 | 71.5% |

> 「红藏品」在原始设计里应是终极稀有掉落。现在它**是保险箱的默认产出**。这是支柱二（揭示爽感）的自我毁灭——当 94.6% 的保险箱都会掉终极物品时，红色揭示音效 4 秒的等待变得毫无意义。

> **结论：本作的经济系统在 2 局内即可通关。** 货币从第 1 局起就不是约束条件，商店实际上是个摆设（玩家更可能直接捡到想要的东西——`premiumBox` 池里有 `tier5_armor`、`rifle_w`、`goldKeycard`）。
>
> 规划文档设想的「5,000–20,000 游戏币/局」「高级装备 50,000–500,000」（`游戏机制与内容丰富计划.md:517-520`）与实际相差 **2–3 个数量级**。
>
> **附注**：商店覆盖率实际是 **100%**（322/322，收集品在 `game.js:606-634` 动态补价），因此「买不到想要的物品」不是问题——**问题恰恰相反，什么都能买到，且一局的钱就够**。

### 5.5 价值密度异常

| 物品 | 稀有度 | 价值 | 重量 | **密度** |
|------|--------|------|------|----------|
| 非洲之星 | ultimate | ₵15,465,000 | 0.3 kg | ₵51,550,000/kg |
| 非洲之心 | ultimate | ₵13,145,200 | 0.3 kg | ₵43,817,333/kg |
| 月光石 | ultimate | ₵3,500,000 | 0.3 kg | ₵11,666,667/kg |
| 红色钥匙卡 | ultimate | ₵2,000,000 | 0.3 kg | ₵6,666,667/kg |
| （对比）步枪 | legendary | ₵250,000 | 1.7 kg | ₵147,059/kg |

**1×1 物品的重量恒为 0.3kg**（`getItemWeight` = `1×1×0.3`，`game.js:52`），而**一块 3×3 的青铜巨像重 2.7kg**。这意味着：
- 最优策略永远是**只捡 1×1 大红**，把 3×3/2×2 的高价值物品全部丢弃（密度更低）。
- 背包的**形状意义被抹平**——所有 1×1 物品等价，格子只是计数的。支柱三（Tetris 背包）的深度被重量公式短路。

## 8. 计算方法说明（可复现）

本文档 §3.4、§5.1、§5.3 的数值由以下方式得出，任何人可复现：

1. 从 `game.js` 中按大括号配平提取 `ITEMS` 与 `CONTAINER_TYPES` 对象字面量；
2. 合并 `COLLECTIBLES_CONFIG`（90 项）与 `RED_COLLECTIBLES_CONFIG`（93 项），并按 `game.js:592-615` 的逻辑把红藏品 id `concat` 进 `safe.items` 与 `premiumBox.items`；
3. 单箱期望价值 =（池内各件 `ITEMS[id].value` 的算术平均）×（`(min+max)/2`）；
4. 揭示时长严格按 `getRevealTime`（`game.js:5297-5309`）的 switch 实现，`africa_star` 单件特判 5.0s；
5. 单局带出模拟：随机抽容器类型（按军事禁区 `containers` 数组的实际类型配比：weaponBox 29 / equipBox 29 / ammoBox 29 / supplyBox 29 / safe 28 / medBox 26），每箱按 min..max 均匀取件数、每件从池中均匀取（与 `game.js:5045` 一致），然后按价值密度降序贪心装箱，受 70kg 重量与背包格数约束。蒙特卡洛 400 次。

> 上述脚本未纳入仓库，因为它是一次性分析工具而非产品代码。若需长期监控平衡，应改为 `tests/balance-sim.js` 并纳入回归。
